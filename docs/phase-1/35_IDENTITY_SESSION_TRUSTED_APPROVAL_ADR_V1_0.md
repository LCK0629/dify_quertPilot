## 2. ID-D01 — Authentication and session (AUTH-D02)
Recommend local pre-provisioned synthetic accounts, fixed issuer urn:querypilot:local:<deployment-id>, immutable random subject UUID; username only lookup alias, never authority. Protected local account file outside registry, Argon2id salted password hashes (minimum 19 MiB, 2 iterations, parallelism 1; calibrate after GO), no plaintext, no self-registration, no password sharing. Separate operator accounts from business accounts; distinct human custody required. Reset by protected operator after identity verification, invalidate sessions and deny until reauthenticated; account creation does not grant rights. Minimum 15-character password or generated equivalent, generic login errors, initial 5 failed attempts per account/source per 15 min with bounded cooldown; no indefinite lockout, no secrets in logs. Verify account enabled and issuer/subject match active registry principal; no client role/scope. Server-side in-memory opaque 256-bit random sessions, hash token in memory, rotate at login/privilege change; 15 min idle, 8h absolute, operator 5 min idle/30 min absolute and fresh reauthentication for approvals. Restart clears sessions. HTTPS same-origin localhost trusted certificate, __Host-qp_session Secure HttpOnly SameSite=Strict Path=/ no Domain; CSRF synchronizer token bound to session for every unsafe request including login/logout (preauth token for login), exact Origin check, reject missing/foreign origin, no cross-origin credentials or wildcard CORS. No localStorage tokens. Protected operator endpoint local only and separately authenticated, no business Admin escalation. Reason: no external provider or session DB for local single process. Risks: password theft/XSS and restart logout; R01. Acceptance ID-01–03: wrong/disabled account, fixation, expiry, logout, cross-origin/CSRF fail; no adapter/SQL for unauthenticated/no-chat; positive login rotates session and resolves only own identity.

## 3. ID-D02 / SR-D03 — Bootstrap and trusted approval
Recommend protected offline enrollment by deployment custodian; record distinct real Security Reviewer and Project Owner operators, verify identities in person or independently controlled channel, assign each separate OS-protected signing key (Ed25519), public keys and capacities in signed/pinned trust manifest outside editable registry. Custodian has separate recovery key held offline; neither business Owner nor users.manage authorizes signing. No shared key or one human pretending to be two reviewers. If independent humans unavailable, activation/release remains blocked; synthetic demonstration may illustrate workflow but cannot claim independent approval. Each reviewer authenticates with separate operator account and fresh reauth, reviews exact canonical manifest and effective-grant diff; signs decision envelope offline or via separately controlled signing utility. Envelope closed schema: purpose POLICY_APPROVAL or RELEASE or RECOVERY, decision, actor principal ID, capacity, policy ID, parent ID, policy digest, trust manifest version/digest, deployment epoch, nonce (128-bit random), issued_at and expires_at (proposed 24h approval window; recovery/release 15 min), target principal/suspension sequence for release, recovery state digest for recovery. JCS UTF-8 with domain prefix QP-APPROVAL-V1 and zero byte; verify Ed25519 signature against pinned key, capacity, purpose, current parent/manifest/epoch, nonce uniqueness, clock and distinct reviewers; creator and changed-entitlement beneficiary excluded. Persist signed envelope in protected content-addressed evidence file; policy_approvals references digest/evidence, unique policy/capacity; activation composite FK binds policy/digest/capacity, only APPROVE accepted; no reuse across purpose/version/epoch. RELEASE binds latest suspension and current policy; consume both nonces in serialized event transaction, no self-release. Rejected candidate requires new sealed version. Reason: lightweight local signing with explicit human accountability; no enterprise PKI. Risk: key loss or collusion, custodian trust. Acceptance SR-17–21/24/27, NEW-01–04, T2-02, ID-04–06: forged capacity, altered digest, stale manifest, nonce replay, same person/key, creator/beneficiary and wrong suspension fail; distinct valid approvals activate one exact candidate.

## 4. ID-D03 / SR-D03 — Canonical policy, activation and trust recovery
Use approved RFC 8785 JCS + SHA-256. Domain QP-POLICY-V1 plus zero byte, UTF-8 no BOM. Closed schema with canonical_version, policy_id, parent_policy_id, version_no, creator_principal_id, created_at, sealed_at, trust_manifest_digest, evaluator_digest, semantic_contract_digest, rpm_digest and explicit OD/metric/output artifact digests; arrays of referenced immutable principals, bindings, roles, permissions and all six versioned state/entitlement relations. Each row includes all authorization-relevant immutable fields from Document 32 including original binding validity, role template and permission meaning digests, stable store IDs, change refs. Sort arrays by tuple of canonical primary key strings, lowercase UUIDs, decimal integer strings no leading zeros, timestamps UTC six fractional digits, explicit null, no Unicode normalization, reject duplicates/unknown fields; hash exact artifact bytes and verify loaded evaluator. Exclude digest itself, approvals, activations and emergency events (separately signed/audited). No mutation after seal including child inserts. Seal under gate, check complete references and every future interval segment, then two independent approvals. Activator revalidates current parent, digest, signer evidence and current trust, atomically inserts activation and audit and switches active pointer. Reject stale/partial state; never reactivate old policy. Golden oracle: reordered object keys same bytes; changed binding interval/template/evaluator different digest; exact full-policy fixture to be independently prepared by QA/DB after design approval; no test claimed.
Trust manifest rotation: custodian recovery key plus distinct Security/Owner signatures on replacement manifest and old/new digest; revoke old keys, invalidate unused approvals, quarantine active analytics until new reviewed policy under new manifest. Lost signer: independently verify replacement identity through custodian and remaining reviewer; require replacement plus remaining independent reviewer to approve recovery, never self-appoint using registry roles; if independent custody unavailable stay quarantined. Preserve evidence; no automatic rollback. Reason: exact reproducibility without distributed signing service. Risk: offline key custody and recovery availability. Acceptance SR-18–21/28, NEW-03/04/10, T2-01/02: tamper/rotation/stale parent/restore denied; atomic failure leaves old pointer intact or quarantine.

## 5. ID-D04 / SR-D04 — Revocation and session coordination
Adopt Document 26 AUTH-D04 gate contract. Session holds identity, not entitlements; check current session, principal, binding, grants, scope and policy each turn and evidence request. No chat.use: 403 before adapter. Stage 2 metric denial: no business SQL, adapter may have run. On logout/reset/suspension/retirement/trust change invalidate affected sessions under same gate, reject new requests, cancel query best effort and suppress buffered result. Emergency suspension independent of publication, committed event overrides policy; binding retirement terminal, RELEASE never restores old binding. Earliest expiry includes all relevant future boundaries; actual UTC time and fresh DB visibility, no streaming, shared cache or persistent answers. No response beyond gate contract; already handed-off bytes R02. Reason: one shared writer boundary prevents stale outputs. Risk: lost sessions and temporary denial. Acceptance RPM-18–21/25/28, SR-22–25/32, DBA-11/12/14, T3-01/02: race, old session, old snapshot and expired grant deny, future valid independent release permits only current grants.

## 6. ID-D05 / SR-D05 — Durable emergency quarantine and recovery
Recommend protected local state directory outside DB, owned by distinct service/maintenance account, restrictive ACL, durable state record with epoch, mode (CLOSED/OPEN/QUARANTINED), monotonic state sequence, pending emergency target or opaque ref, reason and digest; write temporary file, fsync file, atomic replace, fsync directory on supported local filesystem; hold exclusive instance lock. Startup default CLOSED, never auto-open from old OPEN; verify epoch, registry digest, independent audit checkpoint, no unresolved pending emergency, trust manifest and operator-authorized startup; fresh sessions only. Before emergency DB change, under gate persist QUARANTINED/pending intent and stop new handoffs; if gate unavailable set deny latch immediately and stop gateway/disable DB route via protected operator boundary. If suspension+audit commits, verify durable event, clear pending intent and reopen only if no other fault and previous state was valid OPEN; principal stays suspended. If failure/uncertain commit or state persistence fails, keep quarantine, discard queue, invalidate sessions, disable routing, stop gateway when durable state unavailable; no success claim for suspension. Local supervisor startup defaults deny even if crash occurred before marker persisted. Recovery: operator reconciles durable event/audit, verifies DB epoch/current policy and independent checkpoint, repairs/retires affected binding as needed, requires signed distinct Security/Owner RECOVERY envelope bound to state digest; then persist CLOSED, verify again and explicitly open, never recover old answers. If state/keys/backups missing or tampered stay closed; privileged OS/DB tampering R04. Reason: durable deny outside failing DB, no 17th object or distributed coordination. Risk: global outage if one audit write fails; intentional safety preference. Acceptance T4-01/02, NEW-09/10, ID-07/08: disk full, DB down, fsync failure, crash before/after commit, restart, stale marker, unauthorized recovery; no protected result emitted, safe verified recovery positive.

## 7. ID-D06 / SR-D05 — Audit, retention and model egress
Recommend sanitized append-only grant_audit with actor, request, policy/generation, event/action, outcome, reason, opaque target, timestamps, before/after and chained digests; no raw question/SQL, amounts, tokens or secrets. Separate writer/read role; only restricted writer appends, serialize chain; independent reviewer retains digest checkpoint outside DB on protected medium at each policy/approval/revocation and daily request-log segment. Mandatory response audit commit before handoff; ordinary change rollback on audit failure; emergency uses ID-D05. Record authorized-for-handoff not delivery, distinguish unknown commit. Retain request audit 90 days, approval/policy/revocation records project lifetime, controlled purge with independent approval and retained segment anchor; encrypted/access-controlled backups, verify checkpoint and restore under quarantine/new epoch. No claim tamper-proof against privileged host. Adapter receives only minimized synthetic question and generic approved catalog; strip credentials/PII, reject unsafe input, no DB tools or result narrative egress, deterministic explanation only; actual provider/license/retention ADR separate (#6). Success/denial field contract in Document 26, BA must confirm; no raw components or hidden metadata. Reason: small auditable local design. Risk: privileged tamper and provider exposure; R04 and provider decision. Acceptance SR-29, RPM-27, NEW-08/09/14, T5-02, ID-09: audit failure suppresses output, reader cannot release, restore mismatch denied, secret/unauthorized field absent across UI/log/model.
